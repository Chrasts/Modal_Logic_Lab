# Interface design principles

Modal Logic Lab is an interactive environment for learning and experimenting with modal logic through finite Kripke models. Its interface should make that work legible instead of applying one generic page template to every part of the product.

- Top-level activities are **Learn**, **Campaigns**, and **Lab**. Learn contains chapters and lessons. Campaigns contain campaigns and missions; practice is an activity for opening individual missions.
- Use modal notation only when it has semantic content. In particular, `□`, `◇`, world circles, and accessibility arrows are not generic navigation or decoration.
- Petrol identifies current selection and primary interaction. Brown is reserved for a deliberately distinct mathematical role, not a second arbitrary action color. Green and red remain result states.
- The canvas grid belongs to the Kripke workspace. Reading, navigation, reference, help, and settings surfaces use plain paper backgrounds.
- A page's composition follows its function: curriculum progression, mission sequence, reference hierarchy, preference form, or model construction. Do not introduce generic card grids, decorative feature tiles, or repeated eyebrow-heading-rule templates.
- Keep `styles.css` for tokens, shell, controls, and shared workspace rules; keep `relational-design.css` for named application views; keep `mobile.css` for responsive behavior. Replace superseded rules instead of adding a final override sheet.
- Treat `!important` as an exception for accessibility enforcement or narrowly scoped third-party React Flow overrides. App-owned layout and state selectors must win through ownership, specificity, and source order instead.
- Keep App-level orchestration small. Shared shell focus behavior and data-exchange dialog state belong in `app/`; persistent interface-preference parsing belongs in `app/interface-settings.ts`; campaign/profile storage and campaign navigation belong in campaign hooks; authoring draft, mission construction, workflow, library, and session state belong in authoring modules; workspace model state, level loading, guided-session launch, editing commands, verification, attempt recording, Sandbox exchange, undo/redo, presentation, selection, and fullscreen/tour chrome belong in workspace modules. The graph shell, semantic legend, world inspector, table view, result details, and React Flow event wiring are workspace concerns, not `App.tsx` details. New domain state belongs with its controller or feature rather than adding another detailed state flow to `App.tsx`.
